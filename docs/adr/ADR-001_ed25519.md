# ADR-001: Ed25519 for image authentication

- **Status:** Accepted
- **Context:** The boot chain needs an asymmetric signature scheme, so that
  firmware can be authenticated without storing a signing secret on the device.
  The candidates were Ed25519 (RFC 8032) and ECDSA P-256.
- **Decision:** Ed25519, with SHA-256 for payload digests. The OTP fuses hold the
  SHA-256 of the vendor public key; BL2 carries the 32-byte key at the start of
  its payload, and each stage hashes the key and compares it with the OTP value
  before using it to verify a signature.
- **Consequences:**
  - Positive: signing is deterministic, so signing needs no random number
    generator; verification needs none either, which removes a class of
    nonce-related failures. Public keys are 32 bytes and signatures 64. Small,
    simple implementations exist (see ADR-002 and ADR-004).
  - Positive: deterministic signing makes the test vectors reproducible byte for
    byte.
  - Negative: products that must follow a standard requiring NIST curves
    (FIPS 140, some automotive and aerospace profiles) would need a waiver or a
    second algorithm behind the same interface.
  - Negative: one flat vendor key, with no revocation or key hierarchy.
- **Alternatives considered:** ECDSA P-256: larger implementations, per-signature
  randomness unless made deterministic, but accepted by more standards.
- **See also:** ADR-002 (the BL2 implementation), ADR-004 (the BL1 implementation).
